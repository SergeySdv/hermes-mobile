# 01. Архитектура и выбор транспорта

Всё в разделе «целевая структура» — DESIGN. Наличие классов/модулей в upstream не подразумевается. Проверенные первичные источники перечислены в [SOURCES](../SOURCES.md).

## ADR-001 заменён предложением ADR-003

Требование владельца: optional отдельно устанавливаемый APK, не compile-time Rokid flavor.
[ADR-003](../adr/ADR-003-OPTIONAL-ANDROID-ADDON.md) — PROPOSED; его review и gates обязательны
до функциональной реализации. Прежняя встроенная архитектура больше не является целевой.

## Поток и build boundaries

```text
Glasses companion ⇄ Rokid add-on APK ⇄ versioned generic IPC ⇄ Hermes Mobile APK ⇄ VPS
camera/display       Bluetooth/CXR     scoped grant           chat/auth/history
                     local OCR        draft + projection     existing transport
```

Три независимые build units. В Hermes — лишь небольшой generic extension broker и contract
DTO/IDL без hardware dependencies. В add-on — protocol/transport/device settings/OCR/display;
на очках — companion. Общая contract library не зависит от donor common или приложения.
Основной APK один для всех; Bluetooth/CXR не появляются в его dependency graph/manifest.
Add-on имеет собственные package, process, storage и выпуск, но не серверную авторизацию.

G0 обнаружил orchestration в ChatViewModel и отдельный persistence repository, а не готовый
общий repository отправки. Узкий broker адаптируется к существующим attachment target,
composer/outbox и filtered output. Не извлекать весь ViewModel и не создавать второй socket.
Основной клиент выдаёт opaque grant только на выбранный пользователем разговор; scope IDs
и секреты не пересекают IPC. Полные методы, trust и lifecycle — в ADR-003.

Donor hardware код переносится только в add-on/companion после G1/G2. Min SDK/Gradle различия
не требуют массового upgrade Hermes. Никакого импорта donor phone chat/providers/history.

## ADR-002: один транспорт на разговор

Предпочтителен существующий native gateway Hermes Mobile. В просмотренном upstream контракте есть семейства операций с сессиями, изображениями и replay; это лишь кандидат на доступный контракт, не доказательство возможностей VPS [S03].

На G2 нужно заполнить capability matrix: text, image upload, atomic turn binding, stable history, ownership, event replay, cancellation, tool approvals, outcome recovery. Поддержку подтверждать тестом на установленной версии.

Развилка:

1. Native transport проходит обязательные проверки — переиспользовать его и оставить API `:8642` выключенным, если он не нужен другим существующим клиентам.
2. Native transport не умеет необходимую функцию, но есть совместимое обновление — оформить отдельное контролируемое обновление с backup/rollback, не выполнять автоматически.
3. Native transport не подходит, а API подходит — отдельный ADR: сделать API-backed conversation типом общего chat repository. И текст телефона, и очки используют именно его; настройки агента могут по-прежнему ходить через Dashboard. Такой разговор имеет отдельную серверную принадлежность, не притворяется существующим native/Telegram разговором.
4. Ничего не проходит — G2 `BLOCKED`; hardware-моки и независимые тесты разрешены, общий контекст не объявлять реализованным.

Сходство UUID не связывает поверхности. `X-Hermes-Session-Id` не является универсальным способом «подключить любой существующий диалог» [S06]. Не переносить system prompt с динамическим временем и окно последних шести сообщений из donor.

## Единый ввод

Внутри Hermes телефонный composer и принятый IPC draft создают `UserIntent` с уже зафиксированными `conversationId`, `profileId`, `origin`, `operationId`. UI может сменить разговор, но начатая операция не переезжает в новый. Перед upload/submit проверяется, что текущие credentials всё ещё относятся к тому же профилю.

Одна фотография создаёт `Observation`: оригинал, ориентация, capture timestamp, OCR, перевод, связь с выбранным user turn. Локальный перевод не записывается как выдуманное сообщение assistant от Hermes.

## Два пути обработки, один контекст

Fast path: снимок → локальный OCR → локальный перевод → дисплей. Не зависит от auth/сети VPS. Для режима «только перевод» никакого cloud upload.

Agent path v1: явная команда на очках → IPC draft → подтверждение в Hermes → одно сообщение с фото и, если готов, OCR → агент. Автоматический guide/submit требует отдельного ADR и разрешения. Отсутствие OCR не блокирует agent path бесконечно. Поздний OCR сохраняется как локальная аннотация; не запускает скрытый второй turn. При необходимости пользователь отправляет уточнение явно.

Не делаем два конкурентных агентных запроса «описать фото» и «перевести надпись» ради одного снимка. Ведение активной сессии сериализуется, особенно когда backend сначала кладёт image в очередь «для следующего сообщения».

## Как читать результаты сквозного потока

[Наглядные схемы для владельца](../guides/Hermes-Rokid-Integration-Flows.md) разделяют
подключение, agent path, локальный перевод и обратный поток. Для реализации важно различать:
приём фото дополнением → фиксацию draft в Hermes → подтверждённую пользователем отправку →
завершение серверной операции → сохранение результата в Hermes → доставку companion →
применение обновления дисплеем. Успех одного шага не подтверждает следующие.
Staging receipt не означает отправку агенту, а сохранённый ответ не доказывает показ на очках.
Конкретные состояния и подтверждения определяются [контрактами](03-CONTRACTS.md) и
[ADR-003](../adr/ADR-003-OPTIONAL-ANDROID-ADDON.md); новых IPC-методов эта схема не вводит.

Локальный перевод не требует grant на разговор. Для новых агентных запросов нужны
`draft.write` и подтверждение отправки в Hermes; для выдачи ответа — действующий
`assistant.display`. Истечение доступа останавливает выдачу на очки, но не превращает
локальный перевод в серверный запрос и не отменяет уже принятое сервером действие.

## Расширяемость без переусложнения

Внутренние порты add-on не экспортируются как произвольный API Hermes. Внешняя граница —
минимальный IPC v1 из ADR-003. Отсутствие/отключение/удаление/сбой add-on не меняют обычный
chat path. Core выпускается без сборки дополнения и CXR; integration matrix проверяется отдельно.
