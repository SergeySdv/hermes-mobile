# Начало работы для кодинг-агента

Для наглядного знакомства: [схемы потоков для владельца](guides/Hermes-Rokid-Integration-Flows.md).
Это пояснение дизайна на `706a5c96`, не источник новых полномочий; актуальные решения и статусы — в ADR, спецификациях и STATUS.

## Стартовый промпт

```text
Реализуй интеграцию Rokid Glasses в форк Hy4ri/hermes-mobile по этому пакету.

Сначала прочитай upstream AGENTS.md и DESIGN.md, затем этот пакет:
AGENTS.md, specs/00-CONTEXT.md, specs/01-ARCHITECTURE.md,
specs/02-GATES.md, STATUS.md и tasks/T00-BASELINE.md.

Архитектурное уточнение: optional отдельный Android add-on, общий Hermes APK без
Rokid SDK/протокола. Прочитай adr/ADR-003-OPTIONAL-ANDROID-ADDON.md.
До review ADR и допуска gates не начинай функциональную реализацию или prototypes.
G0 BLOCKED в reports/G0-baseline.md; уточнение не изменяет статус.
Сейчас выполняй только T00: инвентаризация, фиксация исходников,
воспроизводимый baseline build и тесты. Не начинай перенос очкового кода,
не меняй production VPS, не обновляй Hermes и не устанавливай APK на устройства
без отдельного допуска на соответствующие действия.

Если нет оборудования, SDK, доступа или секрета: зафиксируй конкретный BLOCKER,
подготовь безопасную проверку для владельца и продолжай только независимую
локальную работу. Не объявляй hardware/backend gate пройденным по мокам.

Не считай имена модулей и типов в плане существующими API. Сначала найди
реальные точки интеграции. Для общего разговора телефона и очков используй
существующий chat pipeline Hermes и один серверный транспорт; не связывай разные
поверхности Hermes произвольным одинаковым session ID.

В конце выдай: изменённые файлы, команды и результаты, отчёт gate,
незакрытые риски, точное следующее разрешённое задание. Не ставь PASS без evidence.
```

## Промпт продолжения

```text
Прочитай STATUS.md, последний gate report и task <TASK_ID>.
Проверь все зависимости этого task, ограничения upstream и ACCEPTED ADR-003.
Без review ADR разрешена только документация, не функциональный код.
Реализуй только его объём. Не меняй соседние модули без обоснования.
Выполни тесты из task и связанного раздела TEST-PLAN.
Подготовь небольшой проверяемый PR, evidence и обновление STATUS.md.
На непроверенном аппаратном/production gate останови зависимую ветку работ.
```

## Режим нескольких агентов

После G0 допустимы две независимые ветки: hardware spike и backend contract audit. У каждой свой worktree. Общие контрактные типы, Room schema и состояние релиза изменяет один назначенный интегратор. Только один оператор управляет реальными очками/ADB в конкретный момент. Только один оператор меняет production конфигурацию в утверждённое окно.

Не коммитить APK, модели OCR, фото пользователя, device identifiers, дампы конфигурации и логи с секретами в обычную git-ветку. Большие приватные evidence хранить отдельно; в отчёте — обезличенный идентификатор, SHA-256, метод и результат.

## Что считать хорошим первым результатом

Не большой PR с тысячами перенесённых строк, а карта фактического кода и воспроизводимая проверка исходного Hermes Mobile. Затем два маленьких доказательства: текст/фото на конкретных очках и безопасный native chat round-trip через конкретный VPS.
