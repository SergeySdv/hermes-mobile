# Hermes Mobile + optional add-on: S1 и проверка через Android Studio

Дата: 28 октября 2026 года.
Назначение: задание основному кодинг-агенту и протокол передачи проверки агенту Android Studio.
Статус: предложенное к исполнению задание по новому приоритету владельца. Реализация, запуск IDE и проверки в рамках подготовки этого файла не выполнялись.

## 1. Решение: начать ограниченную реализацию

Владелец просит перейти от подготовки к работающему прототипу и проверять изменения в запущенном приложении. Первый результат — два взаимодействующих Android APK на эмуляторе, а не ещё один общий архитектурный документ.

Использовать направление ADR-003: обычный Hermes Mobile и отдельное необязательное дополнение. На первом этапе аппаратную часть заменить тестовым дополнением без Rokid SDK. Это проверка настоящего межприложенческого интерфейса, а не объявление поддержки реальных очков.

Ограниченный допуск S1 позволяет писать код общего интерфейса расширений, тестового дополнения и тестов. Незавершённые сборки/тесты донора не блокируют эту независимую работу. Они остаются блокерами соответствующего аппаратного направления и выпуска Rokid.

В первом коммите реализации кратко отразить этот ограниченный допуск и изменённую зависимость S1 в действующих инструкциях/плане. Не оставлять противоречие «любая функциональная работа запрещена» для следующего агента. Не затевать отдельный цикл перепроектирования и не ослаблять требования к безопасности или выпуску.

Исторический G0 не переписывать в PASS. G1/G2, аппаратные результаты, готовность реального VPS и состояние релизных допусков не подменять демонстрацией. ADR-003 не переводить автоматически в ACCEPTED: S1 проверяет выбранное направление в ограниченном объёме. Не заявлять, что задача целиком разрешает production merge, выпуск или изменения сервера.

## 2. Результат первой итерации

На эмуляторе можно воспроизвести:

1. Открыть настоящий Hermes Mobile; обычный клиент работает без установленного дополнения.
2. Установить отдельный `Extension Test Harness` — условное имя тестового APK, не обещание существующего модуля.
3. В Hermes явно разрешить дополнению работу с выбранным разговором.
4. В тестовом дополнении выбрать подготовленный JPEG и текст. Передать их через настоящий IPC, а не прямой вызов внутри процесса Hermes.
5. Увидеть фото и текст в существующем composer Hermes. До подтверждения отправки серверный запрос не выполняется.
6. Нажать существующую кнопку отправки. Применяется существующий путь чата, вложений и транспорта.
7. Увидеть ответ в Hermes и разрешённое отображение этого же ответа в тестовом дополнении.
8. Отключить/удалить/остановить дополнение: обычный чат продолжает работать.

Для первого запуска ответ допускается получить от явно обозначенного тестового backend/адаптера. Использовать существующие точки подмены зависимостей и тестовые средства; не создавать второй чат, отдельную историю и независимый HTTP/WebSocket-клиент.

Mock backend не должен обходить IPC, проверку вызывающего приложения, границы профиля, composer или подтверждение отправки. Фото не подменять нарисованным элементом интерфейса. Отчёт обязан различать:

- `UI + IPC smoke`: настоящий Android IPC и интерфейс, тестовый ответ;
- `backend round-trip`: реальная отправка на разрешённый сервер;
- `hardware smoke`: реальные камера, дисплей и связь очков.

Успех первого пункта не означает успех двух остальных.

## 3. Минимальный объём кода

### Основной Hermes APK

- Общий интерфейс расширений и адаптер к существующему composer.
- Явное включение дополнения и ограничение выбранным разговором/профилем.
- Приём фото/текста в черновик и ограниченное отображение ответа.
- Отзыв доступа; игнорирование запоздавших событий отозванного разрешения.
- Отсутствие зависимости от CXR, Bluetooth-протокола Rokid и донорского приложения.

### Отдельный тестовый APK

- Подключение через тот же версионируемый интерфейс, который впоследствии использует Rokid add-on.
- Выбор тестовой фотографии и текста; кнопка передачи в черновик.
- Экран ответа/статуса и диагностические элементы для отказов.
- Никаких токенов Hermes, адреса VPS, собственной истории или вызовов LLM.
- Никаких Rokid/CXR dependencies. Основной клиент должен собираться без проекта донора и его репозиториев.

### Границы

Имена модулей, методов и команды сборки сначала найти или определить в реальном проекте. Не принимать предлагаемые названия за существующие API.

В первую итерацию не включать OCR-модели, видео, постоянный микрофон, собственный marketplace расширений, auto-submit, auto-renew и масштабный рефакторинг ChatViewModel. Реальный Rokid-транспорт добавляется следующим самостоятельным изменением после достаточной проверки соответствующего пути.

Отладочные данные и подмены backend — только в тестовых/debug-компонентах. Не переносить их в обычную release-сборку. Не вводить глобальное отключение авторизации ради smoke-теста.

## 4. Безопасность не откладывается «на потом»

Применять согласованный контракт ADR-003; точную текущую редакцию проверить в репозитории. Минимальные проверки нужны уже для прототипа:

- проверка разрешённого вызывающего приложения/подписи и согласованной версии IPC;
- явное пользовательское разрешение; связь с конкретным разговором и профилем;
- отсутствие доступа дополнения к auth-секретам и всей истории;
- лимиты входа и управляемый отказ, без скрытого сжатия и отправки;
- отзыв разрешения при соответствующих событиях lifecycle, выходе и смене контекста;
- отсутствие отправки до подтверждения и отсутствие повторного черновика при дублировании одной операции;
- отсутствие автоматического повтора серверного действия при неизвестном результате.

Не ослаблять signature-проверку для удобства тестов. Для положительного тестового пути использовать выделенные тестовые подписи; для отрицательного — другой сертификат. Не использовать production signing keys.

Повторная операция staging и повторное выполнение поручения на сервере — разные уровни. Не приписывать backend идемпотентность без подтверждения его контракта.

## 5. Кто запускает приложение и проверяет UI

Основной агент отвечает за реализацию и доведение проверки до результата. Это не значит, что каждый шаг он обязательно выполняет одним и тем же инструментом.

### Приоритет A: выполнить самому

Если среда основного агента имеет реальный доступ к Android SDK, эмулятору/разрешённому устройству и инструментам управления экраном, он сам:

- собирает и устанавливает debug APK;
- открывает приложения и воспроизводит сценарий;
- проверяет видимое состояние, снимает скриншоты и читает Logcat;
- запускает подходящие автоматические тесты;
- исправляет дефект и повторяет проверку.

Можно использовать имеющиеся Android CLI, adb, тестовый runner или проверенный MCP-инструмент. Сначала проверить доступные команды, версии и конкретное устройство. Новая утилита Android CLI и старый одноимённый SDK executable могут отличаться — одного обнаружения имени `android` недостаточно.

Официальный Android CLI поддерживает установку/запуск, работу с эмуляторами, экранами и UI-иерархиями [1]. Отсутствие открытого Android Studio само по себе не является основанием остановить UI-проверку.

### Приоритет B: передать агенту в Android Studio

Когда основной агент не имеет доступа к устройству, но этот доступ есть у агента Android Studio, подготовить точное задание по шаблону ниже. Встроенный Agent Mode документированно умеет запускать приложение, взаимодействовать с экраном, получать скриншоты и читать Logcat [2].

Использовать автоматическую передачу только при наличии реально настроенного и проверенного канала вызова. Минимальная проверка канала: агент Studio получил task ID, подтвердил рабочую копию/commit и вернул результат без изменения кода.

Не выдумывать CLI-команду, MCP-tool или API для вызова встроенного агента. Записанный Markdown-файл не является выполненной передачей. Если проверенного канала нет, выдать один готовый промпт для запуска в окне Agent Android Studio. Пользователь передаёт задание, но не обязан сам проходить весь тест руками.

BYOA/ACP позволяет запускать выбранного агента внутри совместимой версии Studio. По документации это отдельный экземпляр, запущенный IDE, а не автоматическое подключение к уже работающему агенту терминала [3, 4]. Подключение MCP-серверов к Studio даёт Studio доступ к внешним инструментам; само по себе оно не открывает API вызова Studio из другого агента [5].

Не блокировать S1 разработкой новой системы межагентной оркестрации. Не обновлять рабочие Gradle/AGP/IDE только ради удобства агента без отдельного решения.

### Если ни один агент не имеет устройства

Явно отметить UI-проверки `NOT_RUN`/`BLOCKED`, закончить независимые unit/build-проверки и подготовить запускаемый тест. Не заменять результат скриншотами Compose Preview, сборкой APK или обещанием «это должно работать».

## 6. Передача задания Android Studio

По умолчанию Studio-агент — исполнитель проверки, а не второй независимый автор функционального кода. Один оператор управляет конкретным устройством; не запускать два UI-агента одновременно. Проверять зафиксированный commit в отдельной рабочей копии либо неизменяемые APK, чтобы основной агент не менял тестируемый код во время прогона.

Если Studio-агенту поручено исправление, отдельно передать ему владение конкретными файлами/задачей. После исправления собрать заново и повторить затронутые тесты; evidence старого APK не переносится автоматически.

### Шаблон задания

```text
Ты — агент Android Studio, исполнитель проверки Android UI/IPC.

Task ID: S1-UI-<номер>
Рабочая копия: <реальный путь>
Commit: <полный SHA>
Сборки: <фактические variant/package ID>
APK и SHA-256: <пути/хэши либо точные команды сборки>
Устройство: <разрешённый эмулятор/serial и Android API>
Backend: <mock/test/разрешённый real>; не менять самостоятельно.
Fixtures: <JPEG и тестовый текст без персональных данных>
Evidence: <каталог вне tracked исходников>

Прочитай инструкции проекта. Не меняй функциональный код,
зависимости, подписи, VPS и другие приложения на устройстве.
Работай только с указанными debug/test APK и устройством.

Проверь:
1. Hermes работает без дополнения.
2. Дополнение не получает доступ до явного разрешения.
3. После разрешения фото/текст появляются в composer выбранного чата.
4. До нажатия Send отправок нет; после подтверждения — один user turn.
5. Ответ виден в Hermes и как разрешённый текст в дополнении.
6. Дублирование одной входной операции не создаёт второй черновик.
7. Отзыв/истечение grant и смена контекста блокируют старые события.
8. Сбой/удаление дополнения не ломают основной чат.
9. Неверная подпись/версия и превышение лимитов дают безопасный отказ.

Результат для каждого пункта: PASS/FAIL/NOT_RUN/BLOCKED,
фактические шаги, screenshot/log/test artifact, воспроизводимость.
Проверки сетевых счётчиков, идемпотентности и отсутствия утечки
подтверди тестовыми утверждениями/инструментами: внешний вид экрана
не является достаточным доказательством.

В конце: commit/варианты/APK hashes/device, найденные ошибки,
минимальные шаги воспроизведения, пути evidence и ограничения.
Не объявляй поддержку реальных очков или production-готовность.
```

### Возврат результата

Отчёт Studio-агента должен содержать `task_id`, SHA, APK hashes, устройство/API, режим backend, реальные статусы тестов и доказательства. Основной агент проверяет соответствие результата тестируемой ревизии, исправляет найденные проблемы и инициирует повтор. Он не ставит PASS только потому, что Studio-агент написал «готово».

## 7. Тесты и критерий завершения S1

Нужны оба вида проверок: запуск приложения с взаимодействием через UI и воспроизводимые автоматические утверждения для критичных свойств. Unit tests/успешная компиляция не заменяют UI smoke; визуальный тест не заменяет проверки изоляции, повторов и отсутствия отправки.

Начинать с targeted tests и запуска небольшого сценария. Полный требуемый набор regression/lint выполнить перед merge; не гонять неизменённый полный набор после каждого косметического шага без причины.

Journeys может помочь описывать UI-сценарии естественным языком, но не является обязательной зависимостью. Studio-вариант имеет требования к AGP и ограничения; не обновлять весь проект ради него. Поддержка CLI — отдельный доступный путь при совместимом окружении [6, 7].

S1 готов к review, когда есть:

- функциональный diff, а не только документы;
- два debug APK с точной идентификацией и инструкцией запуска;
- воспроизведённый сценарий фото → draft → явная отправка → ответ;
- базовые позитивные и негативные IPC-тесты;
- evidence запуска и честное описание тестового/реального backend;
- подтверждение работы основного клиента без дополнения;
- известные ограничения и следующий аппаратный шаг.

Отсутствие настоящих очков не мешает выполнить S1, но в отчёте должно быть прямо написано: «Rokid hardware not tested». Нельзя называть тестовый экран дисплеем реальных очков.

## 8. Ветки и PR

Перед началом прочитать актуальные remote refs: состояние PR могло измениться. По сообщению владельца PR #1 уже слит; не использовать его для новой реализации.

Создать отдельную feature-ветку, например `feat/extension-ipc-smoke`, и Draft PR с работающим минимальным сценарием. Не смешивать код с PR #2, предназначенным для ADR/плана, и с продолжением исторических donor-baseline проверок.

Если архитектурные документы ещё только в PR #2, явно указать зависимость или использовать stacked PR с корректной базой; не создавать дубликаты всего пакета и не мержить PR за владельца. В базовой ветке допускается короткая запись ограниченного разрешения S1 и ссылки на нужную редакцию плана.

Незавершённый T00 можно продолжать независимой задачей, когда есть ресурсы. Это не обещание фонового выполнения и не причина откладывать S1. Не переносить ошибки donor build на основной Hermes, если они не затрагивают его фактические зависимости.

## 9. Границы действий

Предпочтительное окружение — отдельный эмулятор с синтетическими данными. Не перезаписывать установленное личное приложение и не очищать его данные для удобства тестов. Установка на личный телефон, операции с очками/pairing, работа с реальными фото, платные запросы и изменения VPS требуют согласованного целевого устройства/окружения и разрешения на конкретные действия.

Не открывать adb/MCP наружу и не создавать публичный доступ к устройству. Не включать секреты, истории пользователя, подписи и персональные изображения в задания агентам или публичные evidence.

```text

Не останавливай независимый от донора S1 только из-за исторического G0.
Отрази ограниченный допуск одним небольшим изменением инструкций
в том же feature PR; не подменяй старое evidence и статусы.

Реализуй настоящий Hermes + отдельный тестовый add-on без Rokid SDK:
JPEG/текст → IPC → существующий composer → подтверждение → существующий
путь чата → разрешённое отображение ответа в дополнении.

результаты UI smoke и список оставшихся ограничений.

VPS и реальные очки этим поручением автоматически не разрешаются.
```
